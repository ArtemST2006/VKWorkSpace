# ghreport

`ghreport` — консольная утилита на Go для сбора информации об открытых Issues в GitHub-репозиториях.

Программа получает Issues через GitHub REST API, фильтрует их по дате создания и формирует JSON-отчёт. Поддерживаются несколько репозиториев, пагинация, повторные запросы при временных ошибках, файловый ETag-кэш и журнал HTTP-запросов.

Это вторая часть [тестового задания](../TASK.md).

Для работы с API используется стандартная библиотека Go, без сторонних GitHub SDK.

## Быстрый старт

Для локальной сборки нужен **Go 1.22+**.

Перейдите в каталог `service/` и соберите приложение:

```bash
make build
```

Получите последние 20 открытых Issues репозитория `cli/cli`:

```bash
./bin/ghreport --repos cli/cli --limit 20 --out -
```

Отчёт будет выведен в терминал в формате JSON.

Чтобы получить Issues из нескольких репозиториев, указать дату и сохранить результат в файл:

```bash
./bin/ghreport \
  --repos cli/cli,octocat/Hello-World \
  --since 2026-01-01 \
  --limit 20 \
  --out report.json
```

Для включения кэширования и журнала запросов добавьте:

```bash
--cache-dir .cache --trace trace.jsonl
```

Для публичных репозиториев токен необязателен. При необходимости его можно передать через переменную окружения:

```bash
GITHUB_TOKEN="your_token" ./bin/ghreport --repos cli/cli --out -
```

По умолчанию используется `https://api.github.com`. Для работы с совместимым API можно указать другой адрес через `GITHUB_API_BASE_URL`.

## Формат отчёта

Пример отчёта для одного репозитория с одной Issue:

```json
{
  "generated_at": "2026-10-25T10:00:00Z",
  "repos": [
    {
      "repo": "cli/cli",
      "error": null,
      "count": 1,
      "issues": [
        {
          "number": 1,
          "title": "Example",
          "author": "octocat",
          "labels": ["bug"],
          "created_at": "2026-01-05T10:00:00Z",
          "url": "https://github.com/cli/cli/issues/1"
        }
      ]
    }
  ]
}
```

Если запрос к одному из репозиториев завершился ошибкой, остальные репозитории продолжают обрабатываться.

## Параметры командной строки

| Флаг | Описание |
|---|---|
| `--repos` | Обязательный список репозиториев в формате `owner/repo`, через запятую |
| `--limit` | Максимальное количество подходящих Issues для каждого репозитория. По умолчанию без ограничений |
| `--since` | Дата создания Issues в формате `YYYY-MM-DD`, включительно, по UTC |
| `--out` | Файл для сохранения отчёта или `-` для вывода в терминал. По умолчанию `-` |
| `--trace` | Путь к JSON Lines-журналу HTTP-запросов. По умолчанию отключён |
| `--cache-dir` | Каталог файлового ETag-кэша. Без флага кэширование отключено |

Репозитории обрабатываются в том порядке, в котором они переданы через `--repos`.

### Переменные окружения

| Переменная | Назначение |
|---|---|
| `GITHUB_TOKEN` | Токен GitHub для авторизованных запросов, необязателен |
| `GITHUB_API_BASE_URL` | Адрес GitHub-совместимого API, по умолчанию `https://api.github.com` |
| `ENV` | Режим работы: `local`, `dev` или `prod`. По умолчанию `local` |
| `LOG_LEVEL` | Уровень логирования: `debug`, `info`, `warn` или `error`. По умолчанию `info` |

Пример переменных для локальной разработки находится в `.env.example`. Файл `.env` исключён из Git.

## Запуск через Docker

Образ собирается из корня репозитория:

```bash
docker build -t ghreport service/
```

Пример запуска:

```bash
docker run --rm ghreport --repos cli/cli --limit 20 --out -
```

При необходимости можно передать токен и адрес API:

```bash
docker run --rm \
  -e GITHUB_TOKEN="your_token" \
  -e GITHUB_API_BASE_URL="https://api.github.com" \
  ghreport --repos cli/cli --limit 20 --out -
```

Docker-образ собирается в два этапа. Приложение запускается от непривилегированного пользователя с UID/GID `65532:65532`.

Токены и другие секреты не включаются в образ. Для сохранения отчётов или кэша в контейнере необходимо предоставить доступный для записи каталог или подключить том.

### Docker Compose

Из корня репозитория также можно запустить приложение через Docker Compose:

```bash
docker compose build
docker compose run --rm -T ghreport
```

По умолчанию отчёт будет выведен в терминал.

Репозитории и лимит можно задать через переменные окружения:

```bash
GHREPORT_REPOS=cli/cli,octocat/Hello-World \
GHREPORT_LIMIT=10 \
docker compose run --rm -T ghreport
```

Чтобы сохранить результат:

```bash
docker compose run --rm -T ghreport > report.json
```

После изменений в Go-коде образ необходимо пересобрать.

## Особенности реализации

### Работа с GitHub API

Для получения Issues используется эндпоинт:

```http
GET /repos/{owner}/{repo}/issues
```

С параметрами:

```text
state=open
sort=created
direction=asc
per_page=100
```

Каждый запрос содержит заголовки:

- `Accept: application/vnd.github+json`
- `User-Agent: ghreport/1.0 (+https://git.miem.hse.ru/blank5204543/vkworkspace)`
- `X-GitHub-Api-Version: 2026-03-10`
- `Authorization: Bearer <token>` — если указан токен

HTTP-запросы выполняются последовательно. Ссылки на следующие страницы берутся из заголовка `Link` с `rel="next"`.

Перенаправления 301, 302 и 307 обрабатываются стандартным HTTP-клиентом Go. Каждая попытка запроса ограничена 30 секундами.

При обработке ответа:

- Pull Requests исключаются по наличию поля `pull_request`.
- Фильтр `--since` применяется локально к `created_at`, без использования API-параметра `since`.
- Дубликаты Issues удаляются по полю `number`.
- Результат сортируется по дате создания, затем по номеру Issue.
- `--limit` ограничивает количество подходящих Issues для каждого репозитория.

### Обработка ошибок

Если запрос одной из страниц завершился ошибкой, результат соответствующего репозитория сбрасывается. В отчёте указывается одна из ошибок:

`not_found`, `rate_limited`, `request_failed` или `invalid_response`.

При этом обработка остальных репозиториев продолжается.

Исключение — ответ **401 Unauthorized**: в этом случае выполнение прекращается.

При временных сетевых ошибках и ответах 5xx выполняются до трёх повторных попыток после первой. Паузы между попытками составляют 1, 2 и 4 секунды.

Для ответов 403/429, связанных с ограничением запросов, также предусмотрены повторные попытки. Время ожидания определяется в следующем порядке:

1. `Retry-After` — количество секунд или HTTP-дата.
2. `X-RateLimit-Reset` — время сброса лимита.
3. 60 секунд — если подходящих заголовков нет.

Ожидание можно прервать сигналом завершения.

### Коды завершения

| Код | Значение |
|---|---|
| `0` | Все репозитории успешно обработаны |
| `1` | Часть репозиториев обработана с ошибками; подробности находятся в отчёте |
| `2` | Некорректные аргументы командной строки; stdout остаётся пустым |
| `3` | Фатальная ошибка с JSON-объектом: `unauthorized`, `all_failed` или `io_error` |

Если не удалось обработать ни один репозиторий, программа возвращает:

```json
{"error":"all_failed"}
```

### ETag-кэш

Для уменьшения количества повторных запросов можно включить файловое кэширование с помощью `--cache-dir`.

Каждому URL соответствует файл:

```text
sha256(URL).json
```

В записи хранятся URL, ETag, заголовок `Link` и тело ответа 200, закодированное в base64.

При повторном запросе используется ETag. Если сервер возвращает `304 Not Modified`, данные берутся из кэша. Сохранённый заголовок `Link` позволяет продолжить обход страниц.

Дополнительно файл `report-<hash>.txt` хранит значение `generated_at` для набора параметров отчёта.

Запись файлов выполняется атомарно. Каталог создаётся с правами `0700`, файлы — `0600`.

Токен не сохраняется. Повреждённые записи кэша игнорируются, а ответ 304 без действующей записи считается ошибкой `invalid_response`.

### Журнал HTTP-запросов

С помощью `--trace` можно записать историю HTTP-запросов в файл формата JSON Lines.

Каждая строка соответствует одному фактическому HTTP-запросу, включая запросы при перенаправлениях.

Поля записи:

| Поле | Описание |
|---|---|
| `ts` | Время запроса |
| `method` | HTTP-метод |
| `url` | Адрес запроса |
| `status` | HTTP-статус |
| `attempt` | Номер попытки |
| `from_cache` | Признак использования кэша |
| `error` | Информация об ошибке |

Заголовки запросов и токен в журнал не записываются.

## Структура проекта

```text
service/
├── cmd/
│   └── ghreport/       # Точка входа CLI
├── internal/
│   ├── app/            # Логика запуска приложения
│   ├── cache/          # Файловый ETag-кэш
│   ├── config/         # Параметры и конфигурация
│   ├── ghreport/       # Сбор и обработка Issues
│   ├── github/         # HTTP-клиент GitHub API
│   ├── lib/
│   │   └── logger/
│   │       └── sl/     # Вспомогательные средства логирования
│   └── report/         # Формирование отчёта
└── bin/                # Собранный исполняемый файл
```

Код разделён по ответственности: работа с API, сбор данных, формирование отчётов, конфигурация, кэширование и логирование находятся в отдельных пакетах.
